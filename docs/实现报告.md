## 4. 一致性收口：实际演示输出

`example_consistency`（规则包：`policies/mapapp/*.json`，7 个实体由**同一份台账**产出）：

```
-- visibleSet(view=situation, name=综合态势) --
  phase=T4   visible=5 excluded=2 nos=[1,2,3,4,5]
  phase=T5   visible=6 excluded=1 nos=[1,2,3,4,5,6]
  phase=T7   visible=7 excluded=0 nos=[1,2,3,4,5,6,7]
  [ok] same view yields 5 / 6 / 7 across phases (rule-driven, explainable)
  [ok] repeated query at the same phase is identical

-- snapshots handed to checkConsistency() --
  view=boardA   name=T4-1 目标列表 items=5
  view=boardB   name=T4-2 目标列表 items=6
  view=boardC   name=T7-2 目标列表 items=7
  view=brief    name=文字稿        items=7

-- consistency report (localized) --
  consistent=false checkedViews=4 checkedItems=25 diffs=5
  no=2   field=flag:hv    kind=missing  views=[文字稿, T4-1 目标列表] expected=present actual=absent
  no=3   field=flag:hv    kind=extra    views=[文字稿, T4-1 目标列表] expected=absent actual=present
  no=6   field=presence   kind=missing  views=[T4-1 目标列表, T4-2 目标列表] expected=present actual=absent
  no=7   field=presence   kind=missing  views=[T4-1 目标列表, T7-2 目标列表] expected=present actual=absent
  no=7   field=presence   kind=missing  views=[T4-2 目标列表, T7-2 目标列表] expected=present actual=absent

-- cross-phase deltas (explainable, basis=current-state) --
  phase=T4   count=5 added=[] removed=[] basis=current-state
  phase=T5   count=6 added=[6] removed=[] basis=current-state
  phase=T7   count=7 added=[6,7] removed=[] basis=current-state
```

**读法**：

1. **"T4-1 五个 / T4-2 六个 / T7-2 七个"** 被逐条定位到**具体编号**（6、7）与**具体视图**（两个展示名）。
   差异性质是"**两个视图不一致**"，而不是"台账不一致" —— 台账是唯一权威。
2. **"高价值 002 vs 003"** 被定位为 `no=2 missing` + `no=3 extra`，且报告点名两个视图。
   台账的权威持有者由 `flagHolders()` 给出（显式动作 + `trace[]` 留痕）。
3. **跨阶段 5/6/7 是规则驱动的合法差异**：同一视图的 `phaseFilters` 在 T4/T5/T7 声明了不同阈值，
   `phaseDeltas[]` 把"多了哪几个编号"列清楚（`basis=current-state`）。
4. **修法只有一个**：界面 MUST 渲染 `visibleSet()` 的结果，MUST NOT 自行过滤（protocol.md CTR-EN-06）——
   自行过滤正是这处矛盾的根因。

另外两处收口演示（`example_minimal`）：评级逐因子可手算（36+23+15+7+5 = 86）与打击窗口
`[now+752000, now+992000)`（`lead=752000 ms`）——**窗口由轨迹外推 + 规则暴露规律算出**，
数值与现状硬编码字符串等价，而引擎内既无该字符串也无该常量（`acceptance.ps1` C10/C10b 机检）。

## 5. 开放问题（**需人类裁决**）

### 5.1 ✅ 已按冻结契约执行、但与需求专篇字面表述冲突的一条

**ELG-ACT-02 / 专篇 §1.4 硬约束**："已升级/已打击的重复请求 MUST 返回 `code=1002 正在执行/已执行`（现状行为保留）"。
**protocol.md §3.3 CTR-EC-01/02 + 冲突裁决 ADR-C15-01/02**："幂等命中 MUST 返回 `code=0` + `data.idempotent=true`；
**MUST NOT** 为幂等成功发明非零 `code`"，理由是 `mapApp/frontend/src/api/client.ts` L38 对任何
`code != 0` **一律抛错** —— 返回 `1002` 会把"已执行"这个**成功**语义变成前端异常。

本实现的落点（三态分离，语义不丢）：

| 情形 | 返回 |
|---|---|
| 重复请求同一动作（已执行） | `code=0`，`status="already-done"`，`data.idempotent=true`（C15） |
| 同一实体动作**正在执行 / 已由他方执行** | `code=1002`，`data.conflict=true`（C16、HTTP 409） |
| 前置条件未满足 | `code=1003` + `unmet[]`（ADR-C16-03） |

`acceptance.ps1` 的 S07-10 与 selftest 的 `act02` 同时断言两条路径，`act02` 还用"宿主 gate 内重入"
真造出并发冲突（`metrics().actionConflicts >= 1`）。
**待裁决**：是把需求专篇 ELG-ACT-02 的措辞改为"已执行语义（`code=0` + `idempotent`）"，
还是走 protocol.md §9 修订流程（会破坏既有前端）。

### 5.2 protocol.md §5.3 的 `kind` 覆盖不足

§5.3 只给了本引擎两个 `kind`（`entityTypes` / `threatFactors`），而规则内容还包括
**动态状态机、去重、置信度融合、旗标、视图与逐阶段过滤、动作集与前置条件、关系种类与两态、
分档阈值、暴露规律、排序键、轨迹参数**。本实现把它们作为 **`items` 的顶层兄弟段**承载
（先例：§5.5 `threatFactors` 的 `bands`、`entityTypes` 的 `numbering`、phase-engine `D-PHE-01`），
因此**没有新增 `kind`**，`acceptance.ps1` C16 严格校验 `kind ∈ {entityTypes, threatFactors}`。
**建议**：protocol 下一版为"动作集 / 视图 / 轨迹 / 关系"登记独立 `kind`（MINOR 变更），
本引擎会一并迁移。

### 5.3 map-2d 回放输入没有"预测点"槽位

`map-2d` 的 `ReplaySample` 只有 `{t, lng, lat, heading?, speed?, props?}`，且 `renderAt` 只把
`id/lng/lat/label/color` 写进图元 —— **`props` 到不了地图图元**，只在 `ReplayState` 与回调里可见。
因此 ELG-TRK-05 的"预测点显式标记"在回放链路上只能落在 `samples[].props.predicted`；
`TrackTimeline.points[]`（本引擎自有形状）里另有显式的 `predicted` 字段供非 map-2d 消费者使用。
**待裁决**：是否请 `map-2d` 增加一个采样点标记字段（跨仓变更，本波 MUST NOT 改）。

### 5.4 需求专篇内部的过期数字

专篇 §0 写"共 **28** 条需求，全部 ⏳"，而 §8 追踪表与逐域相加均为 **41** 条
（ELG-REG 6 + ELG-ID 5 + ELG-RATE 6 + ELG-RANK 4 + ELG-TRK 6 + ELG-ACT 6 + ELG-INTEL 3 + ELG-NFR 5）。
`acceptance.ps1` 以**专篇正文提取的 41 条编号**为基准对账。建议修订专篇 §0 的 28。

### 5.6 其它需要宿主知情的设计取舍

1. **`PhaseContext` 用镜像结构而非 import**：P1 禁止引擎互相 import，故本引擎声明同名同形的五字段结构，
   由宿主从 `phase.phaseContext()` 取值后转交。若后续 protocol 提供共享头，可一行切换。
2. **持久化粒度**：`store->save(missionId, ledger)` 收的是**整任务快照**（写前提交语义的基础）。
   单点轨迹写入会触发一次整任务序列化，故 `appendTrackBatch` 只落盘一次；
   宿主若走高频单点写入，建议注入带写缓冲的实现（`metrics().storeErrors` 可观测失败）。
3. **动作幂等命中仍写一条 `status="already-done"` 日志**（零**状态**副作用：不改台账、不发事件、
   不更新 `updatedAt`）。这样"谁点了第二次"可追溯；若宿主认为日志也不该增长，可后续加规则开关。
4. **`views[].phaseFilters` 首个命中生效**（声明顺序），`"*"` 作兜底；引擎不校验阶段 key 取值
   （阶段名属 `phase-engine` 的规则包）。
5. **`rank.keys` 未声明时的缺省**：`[priority asc, threatScore desc, no asc]`（末位键恒为 `no` 保证稳定），
   已在契约 §4 `TR-ELG-PL-03` 写明缺省。
